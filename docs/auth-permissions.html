Auth is the biggest source of friction when building real apps. The question is almost never "how do I implement OAuth?" and almost always "which pattern fits my situation and what's the minimum I need to configure?" This page covers the four patterns that appear across the stacks on this site, plus how to store credentials safely in each one.

Which pattern fits your situation?

Your situationPatternStack
Local tool, single user, no sharing neededNo authStreamlit + SQLite, Flask local
Calling an external REST API (weather, maps, etc.)API keyAny
Reading/writing Google Sheets from a script or serverGoogle service accountStreamlit + Sheets, GAS
Users log in with their Google account, you control whoOAuth 2.0 (user-facing)Streamlit Cloud, Firebase Auth

Patterns

No auth Local tools — deliberate, not lazy

For tools that run locally and have a single user (you), auth is not a shortcut you're skipping — it's a feature you don't need. Streamlit + SQLite and local Flask apps are both in this category. The tool runs on localhost, access is controlled by who can open the terminal.

The risk surface is: accidental exposure via a shared machine, tunneling, or cloud deployment. If you later deploy a local tool publicly, add auth before you deploy — not after.

If you share your screen or use VS Code Live Share, anyone watching can see and interact with your local app. No localhost is truly private in a screen-share session.
API keys Calling external services

An API key is a long string that proves your code is authorized to call a third-party service. You put it in a request header or query parameter. The key itself is a secret — treat it like a password.

Never hardcode keys in source files. Even in private repos — they show up in git history, pull request diffs, and search results. If you accidentally commit a key, rotate it immediately and treat it as compromised.

Google service accounts Server-to-server access to Sheets, Drive, Gmail

A service account is a non-human Google account your code logs in as. It has its own email address (e.g. myapp@myproject.iam.gserviceaccount.com) and its own credentials JSON file. Use this when your code needs to read or write Google Sheets, Drive, or other Google Workspace resources without a human logging in each time.

Setup steps

Go to Google Cloud Console → select or create a project.
Enable the APIs you need: Google Sheets API, Google Drive API, etc. (APIs & Services → Library).
Create a service account: IAM & Admin → Service Accounts → Create. Give it a name.
Create a JSON key: click the service account → Keys tab → Add Key → JSON. This downloads a file — keep it safe.
Share the relevant Google Sheet (or Drive folder) with the service account email address, just like sharing with a person. Give it Editor access if it needs to write.
In your code, authenticate using the JSON key. Never commit the file — store it in .gitignore and reference the path via an env var.

Using gspread in Python (Streamlit + Sheets)

import gspread
from google.oauth2.service_account import Credentials

# scopes define exactly what the service account can do
SCOPES = [
    "https://www.googleapis.com/auth/spreadsheets",
    "https://www.googleapis.com/auth/drive.readonly",
]

creds = Credentials.from_service_account_file(
    "service_account.json", scopes=SCOPES
)
client = gspread.authorize(creds)
sheet = client.open("My Sheet Name").sheet1
data = sheet.get_all_records()

On Streamlit Cloud — use secrets instead of a file

# secrets.toml — paste the full JSON content as a TOML block
[gcp_service_account]
type = "service_account"
project_id = "my-project"
private_key_id = "abc123"
private_key = "-----BEGIN RSA PRIVATE KEY-----\n..."
client_email = "myapp@my-project.iam.gserviceaccount.com"
# ... rest of JSON fields
# in Python, read from st.secrets directly
creds = Credentials.from_service_account_info(
    st.secrets["gcp_service_account"], scopes=SCOPES
)
The most common mistake: forgetting to share the Sheet with the service account email. The code will authenticate fine but throw a SpreadsheetNotFound or permission error when it tries to open the file.
Google OAuth (user-facing login) Users sign in with their Google account

User-facing OAuth means your app asks the user to sign in with their Google account. You get a token proving who they are, then decide whether they're allowed to use the app. Two variants appear across the stacks:

Variant A — Firebase Auth (React apps)

Firebase Auth wraps the OAuth flow entirely. You call signInWithPopup, Firebase handles the redirect, and you get back a user object with their email and display name. No backend code needed.

import { getAuth, signInWithPopup, GoogleAuthProvider } from "firebase/auth"

const auth = getAuth()
const provider = new GoogleAuthProvider()

async function login() {
  const result = await signInWithPopup(auth, provider)
  const email = result.user.email
  // check against your allowedEmails list
}

Authorization (who is allowed in, not just who they are) is typically handled by an allowedEmails array in a config.json file plus Firestore Security Rules that reject writes from unlisted users.

// firestore.rules — only allow reads/writes from known emails
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /{document=**} {
      allow read, write: if request.auth != null
        && request.auth.token.email in [
          "you@example.com",
          "collaborator@example.com"
        ];
    }
  }
}

Variant B — Streamlit + gspread OAuth

Streamlit Community Cloud can handle Google login via its built-in st.user object when you configure OAuth in the app settings. The user's email is available at st.user.email. Combine this with a role dict to control access per email.

# roles.py — simple email → role mapping
ROLES = {
    "faculty@university.edu": "admin",
    "student@university.edu": "viewer",
}

def get_role(email: str) -> str:
    return ROLES.get(email, "none")
On Streamlit Community Cloud (free tier), OAuth requires your app to be set to Private in the sharing settings. A public app with no viewer restriction won't trigger the login screen even if your code checks st.user.

Scopes and least-privilege

A scope is a declaration of what your app is allowed to do. Requesting a broader scope than you need creates unnecessary risk — if your credentials are ever exposed, the blast radius is larger. Always request the minimum scope that lets your app function.

TaskScope to requestDon't use
Read a Google Sheetspreadsheets.readonlyspreadsheets (allows writes)
Read and write a Google Sheetspreadsheetsdrive (gives access to all files)
List files in a specific Drive folderdrive.readonlydrive (allows deletes)
Send email via Gmail APIgmail.sendgmail.modify or mail.google.com
Read Gmail labels/inboxgmail.readonlygmail.modify
Google scopes are additive — you can always add more later by re-running the OAuth flow. Start narrow and expand only when the code actually needs it.
