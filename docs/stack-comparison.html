This table maps every major function a web app needs — data storage, authentication, API layer, frontend, hosting, and toolchain — across the five stacks in use. Each cell names the specific tool or library, not just the category. Use it to understand what each stack asks you to write, configure, or skip entirely.

Layer 4 — API Layer

#FunctionST-SQLiteST-SheetsFlaskReact-FBGAS-GHP
4.1Define API endpoints None — Streamlit runs frontend + backend in one Python process Flask @app.route decorators None — Firebase SDK talks directly to Firestore; no HTTP API needed doGet(e) / doPost(e) (the /exec URL)
4.2Serialize data None — Python objects passed directly flask.jsonify / Jinja2 template vars Firebase SDK handles JSON automatically ContentService.createTextOutput(JSON.stringify(…))
4.3Validate input Python (manual in pages/) Python (manual in pages/) Python (manual in route handlers) React (manual) + Firestore Security Rules GAS (manual in handler)
4.4Handle errors st.error() (Streamlit) st.error() (Streamlit) flask.abort() + error handlers React try/catch + error state GAS try/catch + ContentService error
The entire API layer disappears in both Streamlit stacks and React-FB. Streamlit because there's only one process. React-FB because the Firebase SDK is a client-side library that talks directly to Firestore — no custom server needed. Flask and GAS are the only stacks where you write explicit endpoints.

Layer 5 — Frontend Rendering

#FunctionST-SQLiteST-SheetsFlaskReact-FBGAS-GHP
5.1Define page structure Python Streamlit widgets (st.columns, st.form, etc.) Jinja2 HTML templates (.html files) React JSX components (.jsx / .tsx) Static HTML files (GitHub Pages)
5.2Style the UI Streamlit default theme + st.markdown CSS injection Static CSS files (static/) CSS / inline styles (no framework currently) Static CSS files (GitHub Pages)
5.3Handle user interactions Streamlit widget callbacks (button, checkbox, selectbox) HTML forms + minimal JS React event handlers (onClick, onChange) Vanilla JS event listeners
5.4Manage frontend state st.session_state (Streamlit) HTML form state + Flask session React useState / useContext Vanilla JS variables + localStorage
5.5Route between pages st.switch_page() (Streamlit multipage) Flask routes + <a href> links React Router (useNavigate, <Link>) Static HTML links / hash routing
5.6Fetch data from backend None — direct Python call, no HTTP hop Full page reload (form POST) or fetch() for AJAX Firebase SDK onSnapshot (real-time) / getDocs fetch() to GAS /exec URL
5.7Render data into UI st.dataframe, st.write, st.markdown (Streamlit) Jinja2 template rendering ({{ var }}) React JSX (map over arrays, conditional render) Vanilla JS DOM manipulation (innerHTML, createElement)
Streamlit collapses 5.1 through 5.7 into Python — there is no HTML, no CSS file, no JS, no fetch call. This is the single biggest trade-off: maximum speed to build, minimum control over appearance and behavior. React-FB is the opposite extreme: every function in this layer is a separate, explicit concern.

GAS-GHP is the only stack with two separate deployment steps and two separate URLs — one for the frontend (GitHub Pages) and one for the backend (GAS /exec). Everything else deploys to one place. Flask and ST-SQLite have no public hosting at all — they exist only on your laptop.

React-FB is the only stack that requires a build step before deployment — you cannot deploy raw JSX to a browser. This adds toolchain complexity (Node.js, npm, Vite config) that the other stacks don't have at all.

The Big Trade-off in One Sentence Per Stack

StackTrade-off
ST-SQLiteMaximum data integrity and developer control; zero deployment story and single-user only.
ST-SheetsNon-developers can edit data directly; you give up schema enforcement, relational queries, and migrations.
FlaskFull control over every HTTP endpoint and template; you write everything yourself with no shortcuts.
React-FBReal-time, multi-user, production-grade scale; highest toolchain complexity and most things to configure.
GAS-GHPZero infrastructure cost and lives inside Google's ecosystem; two separate deploy steps and GAS quota limits cap scale.
